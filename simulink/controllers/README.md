# Controllers

Per-joint controller designs (PID + optional feed-forward / gravity-comp). Each controller is designed against the corresponding plant model in `../plant_models/`, tuned with PID Tuner, and built into a self-contained subsystem block ready for Embedded Coder.

## Planned controllers

| File | Joint | Topology |
|:--|:--|:--|
| `joint_J1_pid.slx` | J1 | Cascaded position → velocity PID; anti-windup; saturation limits |
| `joint_J2_pid.slx` | J2 | Same topology as J1, plus a gravity-compensation feed-forward term (J2 carries the rest of the arm against gravity) |
| `joint_generic_pid.slx` | J3 – J6 | Single-loop position PID parameterized by motor/load constants — one model, many uses |
| `arm_trajectory_tracker.slx` | All 6 | Top-level controller that consumes a MoveIt-style joint trajectory and dispatches setpoints to the per-joint PIDs |

## Design discipline

- **Same controller runs in sim and on hardware.** The controller subsystem is the *exact* block that gets code-generated. No "Simulink-only" simplifications allowed — if a block can't be code-generated by Embedded Coder, it can't be in the controller.
- **Discrete-time, 1 kHz.** All controllers run at the firmware's PID loop rate (`docs/Constraints.md §3a`). Continuous-time blocks (e.g., `Integrator`) are replaced with their discrete equivalents (`Discrete-Time Integrator`).
- **Fixed-step solver, fixed-point safe.** Solver is `Fixed-step, Discrete (no continuous states)`. Where possible, data types are `single` (float32) to match what the STM32 FPU handles natively.
- **All gains exposed as tunable parameters.** Gains are referenced from the MATLAB base workspace (`Kp_J1`, `Ki_J1`, etc.), populated by `scripts/setup_workspace.m`. This makes them runtime-tunable from the firmware once the generated code is integrated, and keeps them out of the model XML.

## Tuning workflow

1. Open `joint_J1_pid.slx` connected to `joint_J1_plant.slx` in a closed loop.
2. Apply a step setpoint (e.g., 45° at t=0.1s).
3. Open PID Tuner on the PID block; tune for the response goal in `docs/Constraints.md` (rise time, overshoot, settling time).
4. Validate against a worst-case load disturbance (rated payload at full extension).
5. Commit the model with updated gains in the workspace setup script.
